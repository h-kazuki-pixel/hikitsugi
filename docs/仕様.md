# 立ち上げ面談とオーナールール — 仕様

最終更新: 2026-11-02 2:30(面談は seed で入れることに決定。チャネルは Slack のみに。入室・報告の遅延の扱いを追加)

## 1. 立ち上げ面談

今回は、この章の7つの塊を設定ファイル(seed)で投入する(下の「今回は seed で入れる」)。会話の面談は、中核がすべて動いていれば短縮版を作る。以下は会話で作る場合の仕様として残す。

目標: 10分で店舗設定が出る。質問は7つの塊。答えが曖昧なら Claude が運営の既定値を提案して確認する(例: 「多くの無人施設では週4回です。それでいいですか?」)。

### 質問の塊
1. 店舗: 店名、業態、営業時間、無人かどうか、休業日の決め方、清掃の型(毎日の店か、週次の巡回の店か)
2. 清掃箇所: 場所の一覧と、それぞれの頻度(毎日 / 週○回 / 来たときに)。例を見せて選ばせる(トイレ・ゴミ・ドリンク周り・床・デスク・ポスト・電池交換・インク補充・階段・エントランス)
3. スタッフ: 呼び名と別名(表記ゆれ用)、人数、出勤の決め方(シフトか自由か)、報告の義務(週○回、誰が対象か、店舗ごとか全店合計か)、週の起算日(既定値は日曜)、免除の制度(試験前など)
4. 報告の手段: Slack のどのチャンネルか。写真を必須にするか
5. 入室記録: 鍵の種類(RemoteLOCK / 他のスマートロック / なし)。スタッフごとの解錠IDがあるか。会員など、スタッフ以外も同じ鍵で入るか(入るなら、スタッフ以外の解錠は保存しない)
6. 連絡先と役割: オーナー、副担当(いれば)。通知の送り先は今回 Slack の DM とダッシュボードに固定し、面談では選択肢を出さない(下の 1-2 参照)
7. 口調と、よく聞かれる質問: スタッフへの声かけの口調(実際に送ったことのある文を1つ)。スタッフからよく聞かれる質問に8〜10件答えてもらい、引き継ぎ帳の初期の知識にする(種別は Claude が付ける。「判断」のものはその場でルール候補として提示してよい)

### 進め方
- 1塊ずつ聞く。1メッセージに質問を詰め込まない
- 答えから店舗設定を少しずつ埋め、途中で「ここまでの設定」を見せる
- 最後に要約を見せ、オーナーが「これでいい」と言えば店舗ページを生成する
- 面談の途中で「こういう時はどうしてほしいか」を聞き、オーナールールを引き出す(2〜3個あれば十分。あとから追加できる)

### 面談が生成するもの
- stores / areas / staff / rules / knowledge の初期データ
- Slack ボットをチャンネルに招待する手順
- オーナー用ダッシュボードの URL

### 今回は seed で入れる
- 同じ内容を設定ファイル(seed)で投入する。面談で聞く7つの塊がそのまま seed の項目になる
- デモでは「会話でも作れる」と口で言うだけにし、代わりに「ルールを自然文で1つ足す → 次の判断経路に原文が引用される」の一往復を画面で見せる

### 1-2. 連絡チャネルの範囲
- 今回作るチャネルは Slack だけ。Web 報告ページは作らない。理由: スタッフ8名の連絡手段が Slack であること(LINE は使っていない)、デモに見せる場面がないこと、日程、主語が「自分の店の不便」
- 受け口は2層にする: 「チャネルアダプタ → 共通の報告イベント」。構造化・畳み込み・エージェントは共通イベントしか見ない
  - 共通の報告イベント: 送信者ID、本文、画像[]、送信時刻、チャネル名、店舗ID(チャンネルから決まる)、スレッド参照(返事を返す先)
  - Slack アダプタ: 署名検証 → 3秒以内に 200 → 共通イベント → キュー。画像は files.info → url_private_download をボットトークンで取得。ボット由来の投稿を弾く
  - Web アダプタ(設計のみ、実装しない): フォーム送信 → 共通イベント → キュー
- 店舗チャンネルには報告以外も流れる。共通イベントにしたあと、まず「清掃報告 / 質問 / 依頼・トラブル / その他」に分類する(両方に当たる投稿は両方)。スレッドに返事を返すのは報告と質問だけ。依頼・トラブルは検出事項としてオーナー画面に出す。その他には何もしない
- README に一文: 「Web や他のチャットはアダプタを1ファイル足せば入る。今回は自分の店のスタッフが全員 Slack なので Slack だけ作った」
- スタッフへの返事(受付・聞き返し・引き継ぎ帳の回答)は元メッセージのスレッドに返す。承認後の声かけは DM
- オーナーへの通知も Slack(DM)とダッシュボードの2つに絞る
- 実店舗用のワークスペースとデモ用のワークスペース(ダミー店舗)は分け、Slack アプリも別に作る。Worker と D1 も環境を分ける。撮影に実データが映る事故をアカウントの段階で防ぐ

## 2. オーナールール

### 自然文の例(店名はデモ用の架空店舗)
- 週4回に満たない人が2週続いたら、私に知らせて
- 祝日と休業日は清掃回数に数えない
- 備品切れは副担当に回して。私には週次の要約だけでいい
- 入室したのに2時間たっても報告がなければ、本人に軽く声をかける下書きを作って
- トラブルありは、すぐ私に
- 同じ人が5分以内に2回送ったら1回扱い
- 薬院店は週1回の巡回でいい。天神店は週4回
- 試験前と申告した人は、その週は数えない
- (引き継ぎ帳から生まれる例)暖房は25度までは自由、それ以上は一声 / 忘れ物は貴重品なら16番ロッカー、ほかは忘れ物BOX / 送風になっているのは仕様、触らなくていい

### 構造(Claude が変換して保存する)
- 元の自然文(画面にはこれを表示する)
- 条件: 何が起きたら(例: 週の報告回数 < 義務回数 が 2週連続)
- 対象: 誰・どこ(スタッフ / 店舗 / 清掃箇所)
- 動作: 知らせる / 下書きを作る / 回数に数えない / 1件に畳む / 義務回数を変える / 判断の基準にする(スタッフへの回答と、報告・写真の検出で参照する)
- 宛先: オーナー / 副担当 / 本人
- 緊急度: 即時 / 定時 / 週次
- 由来: 面談(seed) / オーナーが画面で追加 / 引き継ぎ帳(元の質問と回答の knowledge_id、回答日)
- 状態: 候補 / 有効 / 無効

### ルールの入口は2つ
1. オーナーが自然文で書く(seed、または画面の「ルールを足す」)
2. 引き継ぎ帳の「判断」の回答から。オーナーが答えのない質問に答え、Claude が種別を「判断」と付けたとき、オーナー画面の「ルール候補」に「この答えをルールにしますか」と出す。候補の文面は Claude が自然文で下書きする(元の質問と回答を添える)。オーナーが承認すると状態が「有効」になり、却下すると「無効」のまま引き継ぎ帳の回答としてだけ残る。**承認なしに有効にはならない**

### 判断時の扱い
- 現場エージェントは検出のたびにルール一覧(有効のみ)を参照し、該当したルールの番号と元の自然文、由来を判断経路に残す(例: 「ルール6に該当(11/9 のスタッフの質問から)」)。呼んだツールも経路に残す
- ルール同士が矛盾したら、新しいほうを優先し、オーナー画面に「ルール3と5が重なっています」と表示する
- ルールに該当しない事象は既定値で処理し、判断経路に「既定値」と書く
- 引き継ぎ帳が質問に答えるときも、有効なルールを知識と同じ扱いで参照する(ルールは出典つきの判断として返せる)

## 3. Claude が提案する既定値(現場からの持ち込み)

seed(または面談)でオーナーが決めなかった項目は、この既定値で埋める。README では「なぜこの値か」を書く。証拠は 07(現行運用4か月で実際に起きたこと)とスタッフの質問114件。

| 項目 | 既定値 | 理由 |
|---|---|---|
| 週の起算日 | 日曜(日曜0:00〜土曜23:59 JST) | 学生スタッフの生活リズムと土日の清掃をひとつの週に収めるため |
| 報告の義務 | 週4回。人ごとに全店合計で数える | 無人施設の清掃を維持できる最低線として運営で落ち着いた回数。スタッフはどの店で清掃してもよいので店舗ごとには数えない |
| 回数の数え方 | 送信件数ではなく実施日数(人×JST日付のユニーク) | 1日に複数回送る人と1回送る人を同じに数えるため。送信件数で数えると二重送信が回数を押し上げる |
| 来店時の清掃 | 指定箇所のうち2箇所 | 全箇所を毎回求めると続かない。2箇所をローテーションすれば週4回で一巡する |
| 義務の対象 | 清掃スタッフのみ。オーナー・副担当は対象外 | 運営側の来店は清掃ではないため |
| 免除 | 欠席予定・試験前は分母から外す | 学生スタッフの運用で実際にある制度 |
| 二重送信の畳み込み | 5分 | 送信直後の送り直しが実際に頻発し、集計が二重になったため |
| 報告の保存 | 追記のみ、上書きしない | 現行運用で、同じ箇所を後から報告すると前の記録が消え、繰り越し441件が実は13件だった。スタッフからも「報告フォームの記録が消えた」と質問が来た |
| 店舗の決め方 | チャンネルが店舗を決める。スタッフには聞かない | 現行フォームで店舗欄が空のまま溜まったため |
| 実施日時 | 送信時刻 | 現行フォームで実施日が空のまま溜まり、送信日時で代用していたため |
| スタッフ向けの入口 | Slack だけ(今回) | 「ツールに入れない」という質問が実際に来た。ツールを変えると質問が増える |
| 前日の未清掃 | 繰り越しとして翌日のボードに残す | 消すと忘れられ、残すと翌日に拾われる |
| 未報告の検出 | その日の最終入室(解錠時刻)から2時間後 | 清掃の所要時間と、報告の遅れを許容する幅。退店時刻は鍵から取れないため入室を基準にする |
| 遅れて届いた入室・報告 | 解錠時刻・送信時刻で判定し直し、前提が変われば検出を取り下げる | 鍵の同期エラーで入室が遅れて届くことが実際にある。受信時刻で判定すると誤検出になる |
| 清掃の型 | 毎日の店 / 週次巡回の店 | スタッフがいない店は運営が週1回ほど巡回する。頻度は状況で変わるのでルールで上書きできる |
| 祝日・休業日 | 回数に数えない | 休業日に報告がないのは当然で、注意の対象にしないため(現行運用では未決だった項目。README にそう書く) |
| 休業日の質問 | 答えがなければ「確認中、遅れるかもしれない」と先に返す | 質問の35%は休日に来る。今は代表が休日も即レスで支えている |
| 回答の根拠 | 出典のない回答は出さない | 人が答えたことだけを返す。知らないことは人に回す |
| ルール化 | オーナーの承認でだけ有効になる | 判断の基準を機械が勝手に増やさない |
| スタッフ以外の解錠 | 保存しない | 会員も同じ鍵で入る。会員情報をこの仕組みに入れない |
| スタッフへの連絡 | 必ずオーナーの承認を通す | 機械的な催促は関係を壊す。声をかけるかの判断は人が持つ |

## 4. 報告の構造化(受け口の仕様)

入力: 自由文、または画像(+任意の文)
出力:
- 実施者(Slack ユーザーID または名前の名寄せ。表記ゆれは名簿の別名で解決)
- 清掃箇所[](店舗の areas に照合)
- 備品切れ[](品目)
- トラブル(有無と内容)
- メモ
- 確信度(低いときはスタッフに1回だけ聞き返す。例: 「2階は階段のことですか?」。スレッドに返す)

畳み込み: 同一実施者・5分以内の複数送信は1件にまとめ、元の送信IDを保持する。元の送信レコードは削除しない。

## 5. 現場エージェントの定時実行(概要、詳細は別途)

- 朝(例: 7:00): 前日の未清掃を繰り越し、今日のボードを生成、前日の未報告を検出、オーナー向け朝の要約を下書き
- 夜(例: 21:30): 今日の報告と入室を突き合わせ、未報告を検出、該当ルールに従って下書きを作成
- Webhook 受信時: 報告の構造化、ボード更新、トラブル即時検出、写真・本文を有効なルール(判断の基準)と照合。遅れて届いた入室・報告で前提が変わった検出は取り下げる
- CSV 取り込み時(RemoteLOCK の Webhook が不安定な場合): 取り込んだ入室で夜の突き合わせをやり直す
- 週次(日曜の朝): 週の報告回数を実施日数で集計(免除を分母から外す)、ルールに基づく通知、引き継ぎ帳の更新候補とルール候補を提示
- 判定はすべて解錠時刻・送信時刻で行う(受信時刻ではない)
