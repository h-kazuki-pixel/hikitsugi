## 1. テーマ宣言(提出用。言い回しは 11/7 の台本で微調整する)

スタッフからの質問は約2年で114件。半分は営業時間外に来て、7割は前に答えたことのある内容で、それを自分が休日でも数分で返している。それなのに、次に使える形で残っていた答えは4割に満たない。答えは記録の中ではなく、自分の頭の中にある。清掃も同じで、報告を記録する仕組みは4か月前に自分で作ったが、入室記録との突き合わせは9月末に一度手でやって未報告が10件見つかったきり、声をかけるのも自分だ。記録は溜まるが、判断は人のまま、答えは自分の頭の中のまま。この仕組みは、その判断の部分をツールを持ったエージェントに渡し、同時に自分の運営の判断と現場の知識を、次のスタッフが受け継げる形に残す。

- 選択テーマ: テーマ1「あなたにしかない深さを」
- 対応する方向性: 「ベテランの仕事を次の人が受け継げる形に」「諦めてきた日々の不便を妥協しなくていいものに」「経験や感覚を誰も見たことのない形に」の3つすべて
- 地域との接続(概要文で一段だけ): 福岡の無人施設が地元の高校生・大学生を奨学スタッフとして雇い、地域の学生に勉強する場所を供給している。人手不足の中で無人運営を続けるには、少人数のスタッフとオーナーの間の「見えなさ」を解消する必要がある

## 2. 語り方の原則

- 主語は「自分の店の、自分のスタッフの不便」。汎用SaaSの売り込みに見せない
- 「どのオーナーでも使える」はオープンソースの結果として最後に一言だけ
- 店舗の設定は seed で入れる。デモでは「会話でも作れる」と口で言う程度(10秒)。主役は「報告 → 検出 → 声かけ → 引き継ぎ帳」の毎日の流れ
- 現場の既定値(週の起算は日曜、週4回、二重送信の畳み込み等)を「なぜそうか」込みで語る。理由は4か月の現行運用で実際に起きたこと(07 の表)
- 現行システムの存在を隠さない。「記録は既存、判断は今回」と README の冒頭で線を引く(07)
- デモの山場は「スタッフが休業日に聞いた一言が、翌週には別のスタッフへの答えになり、エージェントの判断基準として判断経路に『ルール6(◯日のスタッフの質問から)』と出る」場面。この作品にしかない瞬間で、テーマ1の「受け継ぐ」の芯
- 「入室したのに報告がない人をエージェントが見つけ、判断経路を出し、声かけ文を下書きする」場面は山場の前振り。ここで判断経路の読み方を一度見せておくと、最後にルール6が経路に出たときに効く
- 写真判定は入口として数秒で流す。山場の引き金が写真であっても、画面は写真ではなく判断経路に寄せる(禁止例「画像解析ツール」との距離)
- 見張る道具に見せない。「サボりを見つける」ではなく「店が汚れたまま夜を越さない」「報告が届かなかったことに気づく」と語る。実店舗では、写真を送ったかどうかを評価に使わないとスタッフに約束した(11/4 のお知らせ)。だから入室の照合は実店舗では動かさず、デモでだけ見せる。声かけ文は責めない。スタッフ側の得(休日でもすぐ答えが返る、聞くストレスが減る)を一言入れる
- 「2か月前の自分」ではなく「今の自分」の不便として語る(照合は今もできていないため)
- 引き継ぎ帳は「休みの日に飛んでくる質問に、答えた本人がいなくても答えが返る」という自分の不便から語る。資料を読ませる話にしない。「自動応答」「チャットボット」「FAQ」「RAG」という言葉は使わない。違いは言葉ではなく仕組みと数字で示す(5-5 の3つの約束と流し直し)
- 場面の題材は、スタッフの質問の実データ(09)と実店舗の運用にあるものだけを使う。想定で作った場面は、実物で確かめてから使う(11/3 の加湿器の教訓)
- 数字は、都合のよくない結果もそのまま出す。流し直しで返せた件数は小さかったが、それ自体が「答えが残っていなかった」証拠になる(11/4)

## 3. 対象のひとり

小さな無人施設(自習室・コワーキング・貸しスペース・24時間ジム)を一人で回し、学生やパートの清掃スタッフを数名抱えているオーナー。デモでは今の自分の不便として語る。

実際の最初の利用者: StudySite の奨学スタッフ7名(2026-11 時点は全員が西新店に在籍。桜坂・原四つ角は募集中)と運営2名(オーナーの橋本、副担当)。西新以外の店舗は副担当が担当する。連絡手段は Slack。

### 3-1. 質問の現実(スタッフの質問114件の集計)
- 店舗の立ち上げは橋本が一人で行う。だから新店舗が増えるたびに「どこに何を置いたか」「なぜこの設計にしたのか」の質問が副担当(主に)やスタッフから橋本に飛んでくる
- マニュアルは紙。スタッフは分からないことがあると紙のマニュアルを見るか、Slack で聞く
- 約2年で114件。49%は営業時間外(休日35%、平日夜14%)。休日はカレンダー比率(33%)より多い
- 68%は過去に答えたことのある趣旨。空調だけで24件を2人が1年にわたって聞いている
- 質問の37%は「どこ」ではなく「していいか・仕様か・どう答えるか」(判断)。紙のマニュアルには書けない種類
- 今はオーナーが休日でも中央値2〜3分で返している。速いのは解決している証拠ではなく、代表が張りついている証拠。答えは代表の頭の中にしかない
- 当時の答えを読み直すと、次に使える形で残っていた答えは114件中44件(39%)。67件は「今から行きます」「待ってください」のようなその場の対応で、3件は答えがなかった。話題は繰り返されているのに、答えは残っていない(11/4 流し直し)
- 人手が足りないので、教える・伝える・引き継ぐことに手を割けない。だから答えが代表の頭の中に残り続ける(11/3 橋本)
- → 引き継ぎ帳が埋めるのはここ。「答えた本人がいなくても答えが返る」「場所だけでなく判断が残る」「その判断を、次からエージェントも使う」

### 3-2. 清掃の現実(11/3 橋本)
- 今の報告は、店舗ごとの清掃完了フォーム。スタッフは実施者を書き、清掃箇所を選んで送る。送ると記録に1行増え、退店の打刻もそれで入る。スタッフはフォームの記録から作られた「清掃状況」の盤面を見て、次に掃除する箇所を選ぶ(11/4 確認)
- 清掃完了と申請されていても、実際は清掃が甘い・汚れていることがある。副担当が見回りで「まだ汚かった」と口頭で知らせてくる。気づくのが後で、気づく人も別の人
- → 写真の確認で、その場で・本人が気づいて直せる形に前倒しする

## 4. 製品の概要

オーナーが店舗の設定を入れると(今回は seed。会話の面談でも作れる設計)、その後は毎日 Claude が現場を見て、未報告や未清掃を見つけ、声かけ文を下書きし、現場の知識と判断を引き継ぎ帳に溜めていく。

### 4-1. 使われるシーン(ある水曜日。店名はデモ用の架空店舗)
- 17:40 スタッフが天神店に入る。解錠が入室として記録される
- 18:25 清掃を終え、店舗チャンネルにトイレとゴミ置き場の写真を送る。トイレの床に紙くずが写っている。スレッドに「おつかれさま。トイレとゴミ置き場、受け付けました。トイレの床に紙くずが見えます。拾ってもらえますか?」。ボードのトイレは「要確認」になる。拾った床の写真を返すと「完了(写真で確認)」になる
- 19:10 別のスタッフが薬院店(週次巡回の店)に入る。21時を過ぎても報告がない
- 21:30 夜の定時。エージェントが入室と報告を突き合わせ、「19:10 入室、報告なし、2時間経過。ルール2に該当。薬院は週次扱いなので緊急度は定時」と判断し、声かけ文を下書き。ダッシュボードに判断の経路が並ぶ
- 21:45 オーナーがスマホで見て、一押しで DM を送る(送らない選択もできる)
- 翌朝 7:00 前日の未清掃は繰り越し、朝の要約が届く
- 土曜(運営会社の休業日)昼 新しいスタッフが「寒いけど暖房上げていい?」と聞く。引き継ぎ帳が「25度までは自由、それ以上は一声(9/14 オーナー回答)」を出典つきで即答する。続けて「席に財布が置きっぱなしだけど、どうすればいい?」と聞く(忘れ物の保管場所は、実データで4人が別々に聞いている)。答えがないので、スタッフには「オーナーに確認します。今日は休業日なので返事が遅れるかもしれません」と返し、オーナーには一度だけ質問が届く
- 日曜夜 オーナーが「財布や携帯などの貴重品は、スタッフだけが開けられる7番のロッカーに保管して。そのほかの忘れ物は、用具棚の忘れ物BOXへ。どちらも、見つけた場所と時間を書いて、忘れ物の写真もつけて報告して」と答える(デモのロッカー番号は架空)。スタッフに返り、引き継ぎ帳に残る。種別が「判断」なので、オーナー画面に「この答えをルールにしますか」と出る。承認すると「ルール6」になる
- 翌週 別のスタッフの清掃報告の写真に、デスクに残ったスマートフォンが写る。報告のスレッドに「デスクの上にスマートフォンが残っているようです。前にオーナーが答えたやり方です:「…」(日曜 オーナーの回答)」と返り、エージェントは「ルール6に該当」として検出し、判断経路にルール6の原文と、その元になった土曜の質問を並べて出す。スタッフが休日に聞いた一言が、次に同じ場面に出会った別のスタッフへの答えになり、エージェントの判断基準になっている
- (11/3 改訂: 当初は加湿器の床置きを題材にしていたが、加湿器は床置きのものしかなく現場に存在しない場面だったため、実データにある忘れ物に差し替えた。実データでは、忘れ物の質問7件のうち5件がその場の対応で終わり、決まりとして残っていなかった)

## 5. モジュール

### 5-1. 立ち上げ面談(今回は seed で入れる)
- 面談で聞く7つの塊(仕様 1章)を設定ファイル(seed)にして投入する。stores / areas / staff / rules / knowledge の初期データは seed から入る
- 会話の画面は、中核がすべて動いていれば短縮版を作る(余力枠の最後)。作らなくても設計は仕様 1章に残す
- 会話で作る場合の仕様: Claude がオーナーに聞き取り、店舗設定を生成する。答えが曖昧なら運営の既定値を提案して確認する。オーナーの判断ルールを自然文で登録できる。最後に設定の要約を見せ、承認で店舗ページが生成される

### 5-2. 報告の受け口(Slack)
- Web 報告ページは今回作らない(スタッフは全員 Slack で、デモにも見せる場面がない)
- Slack: スタッフは普段の店舗チャンネルに文章か写真を送るだけ。Claude が画像を見て清掃箇所を判定し、備品残量・トラブル(ゴミ放置・汚れ)を拾う。受け付けの返事はスレッドに返す。ボット由来の投稿は無視する
- 清掃後の写真に汚れ・ゴミが残っていれば、その箇所は「完了」にせず「要確認」で止め、本人に「拾ってもらえますか」と一つだけ頼む。答えで完了にし、根拠(本人の申告 / 写真で確認)をボードに出す。疑わないが、根拠は見える(11/3 橋本の判断)
- 店舗チャンネルには報告以外(備品依頼・トラブル・違反目撃・雑談)も流れる。投稿を「清掃報告 / 質問 / 依頼・トラブル / その他」に分類し、スレッドに返事を返すのは報告と質問だけ。トラブルは検出事項に回す。「ドアが開かない」のように質問とトラブルの両方に当たる投稿は両方として扱う。オーナー・副担当の投稿は報告として数えない
- ボットへの DM に写真が来たら、本人の主な店舗の清掃報告として受ける。文だけなら引き継ぎ帳への質問
- 受け口は2層: チャネルアダプタ → 共通の報告イベント。構造化以降は共通イベントしか見ない。今回のアダプタは Slack だけ。Web や他のチャット(LINE 等)はアダプタ1ファイルで足せる設計にしておく
- 自由文・画像を構造化: 実施者 / 清掃箇所 / 備品切れ / トラブル / メモ / 残っている汚れ
- 承認済みのルールとの照合は、構造化とは別の呼び出しで行う(11/3 実機: 混ぜると当たらなかった)
- 報告は追記のみ。上書きしない(現行で上書き事故が起きたため)
- 同一人物の5分以内の二重送信は1件に畳む(元の送信は残し、参照で結ぶ)。畳んでも受付は返す
- 1回の投稿で読む写真は6枚まで(箇所ごとに1枚、まとめて送ってもらうため)。室内は撮影禁止の店があるので、文だけの報告も報告として受ける(11/4)
- 店舗チャンネルには現行のフォームの通知(Notion のボット)も流れる。ボットの投稿として読まない

### 5-3. 現場エージェント(中核)
- Claude にツールを持たせ、定時(朝・夜)と Webhook 受信時に動く
- ツール: 入室記録を読む / 報告を読む / 名簿を見る / ルールを参照する / 下書きを作る / ボードを更新する / 引き継ぎ帳を検索・追記する
- ルールには面談(seed)で登録したものと、引き継ぎ帳の「判断」から承認で生まれたものが同じ一覧に並ぶ。エージェントはどちらも同じように参照し、判断経路には該当ルールの原文と、ルールの由来(面談 / ◯月◯日の質問)を出す
- 判断の経路をオーナー画面に表示する。エージェントが呼んだツールも経路に出す(例: 「入室記録を読む → 報告を読む → 報告なし → ルール一覧を参照 → ルール2に該当 → 声かけ文を下書き」)。ツールを持って判断していることが画面で分かるようにする
- 入室・報告は遅れて届く前提にする(鍵の同期エラーが現実に起きている)。判定は受信時刻ではなく解錠時刻・送信時刻で行う。遅れて届いた入室や報告で前提が変わったら検出を取り下げ、取り下げたことも判断経路に残す。承認前の下書きは取り下げと同時に消える
- 実装は Anthropic SDK のツール使用ループを Worker 内に実装(Agent SDK は Node 前提のため不使用)

### 5-4. 承認つきの発信
- スタッフ宛ての声かけ・催促は Claude が下書きし、オーナーが一押しで送る(Slack の DM)。送らない選択もできる
- スタッフ宛てに承認なしで送るのは、スタッフが送ってきたもの(報告・質問)へのスレッド返事だけ(受付、聞き返し、汚れを拾ってもらう一言、引き継ぎ帳の回答、引き継ぎ帳から生まれたルールに当たったときの元のオーナーの回答、「確認中。休業日なので返事が遅れるかもしれない」)。スタッフへの文のうち、回答・ルールの部分はオーナーの言葉の原文と出典をコードが並べ、Claude には作らせない
- オーナー・副担当宛ての通知(答えのない質問の確認、トラブルの即時通知、ルール該当の通知、備品切れの回送、朝の要約)は承認なしで送る。宛先が運営側なので、承認すること自体が成り立たない(承認する本人に届くものを、本人が承認することになる)
- スタッフへの自動送信はしない(運営の実感に基づく設計。README で理由を書く)
- DM はボット名義で届くので、文面はオーナーの口調サンプルに寄せ、末尾にオーナー名を添える(機械的な催促に見せない)。責める文面にしない

### 5-5. 引き継ぎ帳
- スタッフや副担当が Slack で質問(店舗チャンネルの投稿、またはボットへの DM)→ Claude が店舗の知識から答える。回答には出典(誰がいつ答えたか)を添える
- 知識には種別を持つ: 場所(どこに何があるか)/ 手順(どうやるか)/ 判断(していいか・仕様か・どう答えるか)。114件の実データで判断が37%、手順36%、場所27%
- 知らなければオーナーに一度だけ聞き、次からは答えられる。休業日(店舗設定の休業日カレンダー)に答えのない質問が来たら、スタッフには「オーナーに確認する。休業日なので返事が遅れるかもしれない」と先に返す。これは自分で送ったものへの返事なので承認は要らない
- オーナーに確認中の同じ質問が別の人から来たら、二度は聞かず、答えが来たらその人のスレッドにも返す
- 有効なルールも、知識と同じ扱いで出典つきの判断として返す
- 報告やトラブル対応の記録からも知識が溜まり、店舗ごとの運営マニュアルが育つ
- 紙のマニュアルは取り込まない。知識はオーナーや副担当が実際に答えた言葉からだけ溜める。seed で「よく聞かれる質問」に8〜10件オーナーが答え、それを初期の知識にする
- 「何が聞かれたか」中心で残し、質問の回数を人の評価として表示しない
- 最小形(知らない質問 → 確認中と返す → オーナーに一度聞く → 次から出典つきで答える)を早めに動かし、休業日に来る質問を確実に拾う

#### 引き継ぎ帳の3つの約束(「チャットボット」「RAG」との違いを仕組みで示す)
1. **出典のない回答は出さない。** 過去に人が答えた言葉に当たるものがなければ、生成して埋めずに「分からない」と言って人に回す。スタッフへの文は Claude に書かせず、回答の原文と出典をコードが並べる。テストで示す: 検索で見せていない知識を選んだとき、文章だけで答えたとき、回答が送られず人に回ることを確認する。出典のない回答が0件なのは、コードが文を組むことによる作りの保証。流し直しで確かめたのは、その保証が実データでも崩れないこと(3回とも0件)。実データで見えた本当の弱点は、出典つきで返したのに当てはまらなかった1件(README の限界)
2. **判断の答えは、エージェントの判断基準になる。** 種別が「判断」の回答がオーナーから返ると、オーナー画面に「この答えをルールにしますか」と出る(ルール候補)。承認すると自然文のルールとして登録され、以後の検出・声かけの下書きでエージェントが参照する。ルールには由来(元の質問と回答の日付)が残り、判断経路に出る。質問から入ったものが、エージェントの行動を変える。候補の提示は Claude が種別を見て行い、ルール化はオーナーの承認でだけ起きる
3. **単独の画面にしない。** 引き継ぎ帳は現場エージェントのツールの一つで、報告・検出・声かけと同じ流れの中にある。デモでは「休業日に来た質問」の文脈で見せ、ルール6の山場につなげる

#### 過去の質問の流し直し(11/4 0:50 実データで実行。位置づけを変更)
当初は「代表を呼ばずに返せた件数」をインパクトの主な数字にする予定だった。実データで回すと、帳に積める答えがほとんど残っていなかった。そこで流し直しは、「答えが残っていなかった」ことの証拠と、約束1が守られていることの証拠として使う。
- 方法: 引き継ぎ帳を空から始め、過去の質問114件を時系列で流す。各質問の時点では、それより前に人が答えた内容のうち、次に使える形の答え(再利用できる答え)だけを知識として持たせる。その場の対応は積まない。答えの時刻は質問の時刻で近似した(実際の回答時刻で確かめ、未来の答えが見える組は0件)
- 当時の答えの分け方(LINE のトーク履歴と Slack のスレッドから): 再利用できる答え44件 / その場の対応67件(「今から行きます」「待ってください」「それです(写真を見て)」など)/ 答えなし3件
- 結果: その時点の帳にそのまま答えがあった質問は3件(Claude の判定)。出典つきで返せたのは1〜2件(3回の実行で 2・1・2)。出典のない回答は3回とも0件(作りの保証が実データでも崩れなかった)。返したもののうち、当時実際に返した答えと趣旨が合わないものがあった(内訳は README の限界に書く)
- 読み方: 話題の7割は繰り返されているのに、次に使える答えとして残っていたのは4割に満たず、その時点で帳が答えられた質問は114件中3件だった。答えは記録にも残らず、その都度代表が返していた。引き継ぎ帳の役目は過去を掘り起こすことではなく、これからの答えを、次の人とエージェントが使える形で残すこと(判断の答えはルール候補になる)
- 返せた件数を増やすためにプロンプトを緩めない。母数が3件で根拠にならず、緩めると約束1の側へ寄るため
- 実名入りの元データは非公開の環境でだけ回す。公開するのは件数と割合だけ。リポジトリには同じ評価スクリプトを架空データつきで置く

### 5-6. 時間が足りないときに切る順番
中核は「Slack報告 → 構造化 → 入室との突き合わせ → ルール照合 → 判断経路 → 承認つき下書き」の一本。これが公開のデモ環境で通しで動いていることが最優先。実店舗では入室との突き合わせを除いて動かす(11章)。
1. 立ち上げ面談を seed に → 実施済み
2. 引き継ぎ帳を最小形に絞る。報告からの自動蓄積を落とす → 残る削り代はこれ
3. Web 報告ページを落とす → 実施済み
どれだけ削っても残すもの: 判断経路の表示、承認の一押し、報告を上書きしない設計、引き継ぎ帳の最小形(ルール候補を含む)、過去の質問の流し直し

削ってもテーマ1の「受け継ぐ」の芯として画面で見せる一往復:
- オーナールール: 自然文で1つ足す → Claude が構造化 → 次の判断経路にその番号と原文が引用される
- 引き継ぎ帳の最小形: 知らない質問 → スタッフに「確認中(休業日なら遅れる)」と返す → オーナーに一度聞く → 次から出典つきで答える → 判断の答えはルール候補になり、承認で次の判断経路に出る

- ボードの状態: 完了(根拠: 報告 / 本人の申告 / 写真で確認)/ 未清掃 / 繰り越し / 要確認 / 対応者不在
- 見た目の仕上げは 11/5 午前。動画に映る画面(判断経路・ボード・承認待ちの下書き・ルール一覧と候補・Slack の文面)だけを、前提知識のない人が読めるように直す。新しい機能は足さない

## 7. 技術構成

- Cloudflare Workers(有料プラン)+ D1 + Queues + Hono(HTML は Hono の JSX で描画、スマホ優先)
- 定時実行: Workers Cron Triggers(朝・夜)。Cron はキューに積むだけ
- Claude: Anthropic SDK、ツール使用ループ、画像入力(写真判定)。製品内のモデルは、報告の構造化・写真判定・ルールの照合が claude-sonnet-5-5、現場エージェント(引き継ぎ帳を含む)が claude-opus-5-5。README に役割ごとに選んだ理由を書く
- Slack: Events API(message.channels / message.im / file_shared)を Worker で受信。署名検証して即 200、処理はキュー。画像は files.info → url_private_download をボットトークンで取得して Claude へ。返事は chat.postMessage(thread_ts)、承認後の声かけは DM
- 入室記録: 汎用の入室イベント受け口(POST /events/entry)。RemoteLOCK の2つ目の通知先としてこれを登録する(既存の通知先には触らない。手順は 07 の5)。会員の解錠も同じ Webhook で飛ぶので、受け口で名簿の解錠IDと照合し、スタッフ以外は保存せず捨てる(元ペイロードも残さない)。デモ用に「入室を模擬する」ボタン
- 実店舗では入室の受け口を作らない(11/4 決定。11章)。下の CSV も同じ
- RemoteLOCK の Webhook が安定しない場合は、管理画面から書き出した CSV を取り込む入口を足し、同じ入室イベントに変換する。オーナーが夜に一度上げれば、突き合わせと下書きはエージェントが行う。スタッフ以外の行は取り込み時に捨てる。デモは模擬ボタンなので影響を受けない
- 実店舗用とデモ用で Worker と D1 を分ける(wrangler の環境を2つ。Slack アプリが2つなのと揃える)。実店舗用のオーナー画面は Cloudflare Access で保護する。デモ用は架空データのみなので公開でよい。demo の D1 は reset-demo ワークフローで作り直せる
- Notion は使わない(現行システムと基盤から分ける)
- 公開リポジトリには架空の店舗データのみ。実店舗データは本番の D1 にだけ存在する

## 8. データモデル(概略)

「上書きしない」ものは、更新せずに版や回答を積んで表す。報告の原本・構造化の版・引き継ぎ帳の回答は、DB のトリガーで更新と削除を止める。

- org_settings: 運営全体の設定(1行。週の起算日、週の実施日数、来店時の清掃箇所数、出勤の決め方、免除の制度、二重送信の畳み込み分、未報告とみるまでの分)。報告の義務は人ごとに全店合計で数えるので、店舗ではなくここに持つ
- stores: 店舗設定(名前、業態、営業時間、清掃頻度の型[日次/週次]、休業日、報告のチャンネル、鍵の種類、口調サンプル)。店舗ごとの頻度の違いはルールで上書きする
- areas: 清掃箇所(店舗、名前、頻度)
- staff: スタッフ(呼び名、別名[]、Slack ユーザーID、解錠ID、在籍状態、義務の対象か、役割[スタッフ/副担当/オーナー])
- absences: 欠席予定・免除(スタッフ、期間、理由区分)
- reports: 報告の原本(送信者、送信時刻、受信時刻、元テキスト、画像ID、チャネル[手段・チャンネル・メッセージID]、畳み込み元)。受け取ったものだけを持ち、追記のみ
- report_versions: 報告の構造化結果の版(報告、版番号、実施者、清掃箇所[]、備品切れ[]、トラブル、メモ、確信度、根拠[構造化/スタッフの返事/オーナーの修正]、モデル)。Claude の構造化が版1、聞き返しで確定したら版2として積む。今の姿は最新の版を読む(reports_current)
- clarifications: 聞き返し(1報告に1回)
- entries: 入室イベント(スタッフ、解錠時刻、受信時刻、デバイス、取り込み元[Webhook/CSV/模擬]、元ペイロード。スタッフ以外の解錠は保存しない)
- board_items: 日次ボード(日付、店舗、箇所、状態、繰り越し元、要確認の理由、完了の根拠)
- rules: オーナールール(元の自然文、条件、対象、動作、宛先、緊急度、読み取り、由来[面談 / 画面で追加 / 引き継ぎ帳の knowledge_id と回答 id]、状態[候補/有効/無効])
- findings: エージェントの検出(日時、種別、対象、根拠、該当ルール、判断経路、状態[有効/取り下げ])
- drafts: 下書き(宛先、本文、状態: 承認待ち/送信済み/却下/取り下げ、承認者)。スタッフ宛ては承認者なしに送信済みにできない
- knowledge: 引き継ぎ帳の質問(質問、種別[場所/手順/判断]、聞いた人と日時、質問の場所、オーナーに聞いた日時と問い合わせ先、状態[回答済み/オーナー確認中])
- knowledge_answers: 引き継ぎ帳の回答(質問、回答、出典[誰がいつ]、置き換えた回答)。追記のみ。答えが変わったら新しい回答を積み、前の回答と出典は残す。今の答えは最新の回答を読む(knowledge_current)。過去の質問の流し直しでは、その時点までの回答だけを読む
- knowledge_waiters: 確認中の質問を待っている人
- claude_usage: 製品の中の Claude 呼び出しの消費(種類・モデル・トークン数・写真の枚数・上限で切れたか。本文は持たない)

## 9. 既定値(現場からの持ち込み。理由と証拠は仕様 3章・07)

- 週の起算は日曜
- 報告は週4回。送信件数ではなく実施日数で数える。人ごとに全店合計で数える(店舗ごとではない)。だから義務の設定は店舗ではなく運営全体の設定に持つ
- 来店時は指定箇所のうち2箇所を清掃する
- 義務の対象は奨学スタッフのみ。オーナー・副担当は対象外
- 試験前免除・欠席予定は分母から外す
- 二重送信の畳み込みは5分
- 報告は追記のみ、上書きしない。受け取った原本と構造化の結果を分け、聞き返しで確定した内容は版として積む
- チャンネルが店舗を決める。送信時刻が実施日時
- 前日の未清掃は「繰り越し」として翌日のボードに残す
- 清掃後の写真に汚れが残っていれば「要確認」。完了には根拠(本人の申告 / 写真で確認)を残す
- 未報告の検出は、その日の最終入室(解錠時刻)から2時間後
- 入室・報告が遅れて届いたら検出を取り下げる
- 祝日・休業日は回数に数えない(店舗の休業日設定を参照)
- 店舗ごとに清掃の型が違う(毎日の店 / 週次巡回の店)。週次巡回の店は状況で頻度が変動するので、ルールで上書きできるようにする
- 休業日に答えのない質問が来たら、返事が遅れることを先に伝える
- 出典のない回答は出さない
- 引き継ぎ帳の回答は追記のみ。答えが変わっても前の回答と出典は残す
- ルール化はオーナーの承認でだけ起きる
- スタッフ宛ての声かけ・催促は必ずオーナーの承認を通す。例外はスタッフが送ってきたものへのスレッド返事だけ。オーナー・副担当宛ての通知は承認なしで送る

## 10. やらないこと

- 複数店舗の横断ダッシュボード(店舗単位で完結させる)
- Notion への書き出し・読み出し
- 紙のマニュアルの取り込み(5-5 の理由)
- 利用者(会員)に直接答える仕組み。引き継ぎ帳が答えるのはスタッフと副担当まで
- 決済・会員管理
- スタッフ宛ての自動送信(スタッフが送ってきたものへのスレッド返事を除く。運営宛ての通知は 5-4 のとおり承認なしで送る)
- 承認なしのルール化
- 副担当の見回りの指摘を投稿で受けて要確認に戻す経路(人の清掃を後から検める形に寄るため。実稼働の件数を見てから考える)
- Web 報告ページ(アダプタ層は残す)
- 会話での立ち上げ面談(seed で入れる。余力があれば短縮版のみ)
- Slack 以外のチャット(LINE 等)。アダプタ層は用意するが実装しない
- 音声メッセージの文字起こし(範囲外)
- 退店時刻の取得(RemoteLOCK では取れない)
- 実店舗での入室の照合(フォームが主のまま並走するので、フォームだけの人が「報告なし」になる。写真の有無を評価に使わないとスタッフに約束した。11章)
- 現行のフォームの置き換え(退店の打刻と清掃状況の盤面がフォームで動いている)
- 既存コードの再利用(ルール上禁止。設計の知見のみ持ち込む)
- 流し直しで返せる件数を増やすための調整(5-5 の理由)

## 11. 実店舗稼働
