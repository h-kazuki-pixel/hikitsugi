# 07 現行システムとの線引き

作成: 2026-11-01 / 更新: 2026-11-02
目的: 2026-07 から運用している清掃管理の仕組み(Claude と作成、非公開)と、ハッカソンで新規に作るものの関係を明確にし、「既存コードの再利用」「期間中に作ったと判別できない」の2つの失格条件を避ける。個人名は書かない

## 1. 現行システム(2026-07〜、ハッカソンの提出物ではない)

| 要素 | 内容 |
|---|---|
| スタッフの報告 | Notion フォーム(店舗別・匿名・Notion アカウント不要)。Slack の店舗チャンネル上部のタブから開く。項目: 実施者 / 清掃箇所(複数選択) / 備品切れ / 不足品目 / トラブル / メモ。写真なし。スタッフは Notion ではフォーム送信しかできない設定 |
| 記録先 | Notion「清掃完了ログ」DB。同じ親に「清掃チェックボード」「欠席予定」「スタッフ名簿」「来店ログ」(2026-08 追加) |
| スクリプト | 非公開リポジトリの Python スクリプト。GitHub Actions で JST 7:00〜21:45 の15分おき。前日未清掃を「繰り越し」に、当日の店舗×箇所レコード生成、ログとボードの突合 |
| 入室記録 | 単機能の Cloudflare Worker。RemoteLOCK 解錠 Webhook → 来店ログ DB。名寄せを Worker 内に実装。スタッフと会員の解錠は区別して運用中 |
| Slack 通知 | Notion オートメーション(清掃完了ログにページ追加 → 西新店チャンネルへ投稿)。Slack ボットはない |
| それ以前 | 清掃完了は紙の清掃表に記入。Slack には備品依頼・トラブル・違反目撃のみ |

### やっていること / やっていないこと
| 機能 | 現行 |
|---|---|
| ボード反映・繰り越し | 自動 |
| 清掃完了の Slack 通知 | 自動(西新のみ、2026-09〜) |
| 未報告の検出 | **手動、一度だけ**。9/28 に RemoteLOCK の CSV を Claude に渡して照合し、「入室したのに報告なし」10件を検出。手間がかかり、以後やれていない |
| 入室記録と報告の照合 | **手動、一度だけ**(入室は自動記録されるが、照合は 9/28 の1回のみ) |
| スタッフへの声かけ | **手動**。文面は毎回 Claude に下書きさせる |
| 週の回数集計 | **手動、毎週**。8/4 に「計算はするが DB には書かない」と決め、以後毎週 Claude に頼む |
| スタッフの質問への回答 | なし |
| トラブルの即時アラート | 採用決定のみ、未実装 |

→ **記録は揃っている。判断は全部、人がやっているか、手が回っていない。** これが今の自分の実像。

## 2. ハッカソンで作るもの(別物)

| | 現行 | 新規 |
|---|---|---|
| 役割 | 記録 | 判断(検出・ルール照合・下書き)と引き継ぎ |
| 基盤 | Notion + GitHub Actions(Python)+ 単機能 Worker | Cloudflare Workers + D1 + Queues + Hono(TypeScript)。Notion を使わない |
| 報告の入口 | Notion フォーム | Slack に写真か一言(構造化は Claude) |
| 入室 | RemoteLOCK → Notion 来店ログ | RemoteLOCK の2つ目の通知先 → 汎用 POST /events/entry → D1(スタッフ以外は捨てる)。不安定なら CSV 取り込み。デモは模擬ボタン |
| Claude の位置 | 運営者が手で呼ぶ(集計は毎週、照合は一度) | ツールを持ったエージェントが定時と Webhook で動く |
| コード | 非公開、2026-07 作成 | 公開、全て 11/2 12:00 以降。既存コードは一行も持ち込まない |

ボード・繰り越し・名寄せは新規でも作るが、知見だけを持ち込み、コードはゼロから書く(設計の知見の持ち込みはルール上問題ない。コードの再利用が失格)。

## 3. README に書く一段(案)

> 2026年7月から、Notion フォームと GitHub Actions で清掃報告を記録する仕組みを運用してきた(別リポジトリ・非公開・本ハッカソンの提出物ではない)。4か月やって分かったのは、記録は溜まるが、判断は人のまま、ということだった。週の回数は毎週自分が Claude に数えさせている。入室記録との突き合わせは、9月末に一度 CSV を渡してやってみたら「入室したのに報告がない」が10件見つかったが、手間がかかってそれきりになっている。声をかけるのも自分だ。この仕組みは、その「判断」の部分を、ツールを持ったエージェントに渡すために、基盤からゼロで作り直したものである。既存のコードは一行も含まない。

## 4. 現行運用の困りごと → 新規の既定値(証拠つき)

| 困りごと(現行で実際に起きた) | 新規の既定値 |
|---|---|
| 上書き: 同じ箇所を後から報告すると前の記録が消えた。復元後、繰り越し441件が実は13件だった | 報告は追記のみ。上書きしない。1送信=1レコード、畳み込みは別レコードを参照で結ぶ |
| 表記ゆれ(本名/あだ名/ローマ字) | 名簿で名寄せ。確信度が低ければ1回だけ聞き返す |
| 店舗プロパティが空(店舗別フォームで店舗を聞かないため) | チャンネルが店舗を決める。聞かない |
| 実施日が空で送信日時で代用 | 送信時刻を実施日時とする。JST で日付を切る |
| 二重送信(数秒〜数分内) | 5分以内の同一実施者は1件に畳む |
| cron のスキップ、無料枠超過、Notion API 障害 | Workers Cron + Queues。外部 SaaS の API に依存しない |
| 内部リンクを配ってスタッフが開けなかった | スタッフ向けは Slack だけ |
| RemoteLOCK は退店が取れない | 退店は扱わない。「最終入室から2時間後」で未報告を見る |
| RemoteLOCK の過去の解錠履歴は API で取れない | 入室は Webhook で受けた時点で自分の D1 に貯める |
| 入室の照合に CSV の書き出しと手作業が要り、一度しかやれなかった | 入室が届いた時点で D1 にあるので、夜の定時にエージェントが毎日突き合わせる |
| 鍵の同期エラーで入室が遅れて届く | 解錠時刻で判定し、遅れて届いたら検出を取り下げる |

### 既存運用から持ち込むルール(仕様の既定値表に反映済み)
- 週の起算は日曜(日曜0:00〜土曜23:59 JST)
- 義務は週4回。**送信件数ではなく実施日数**(人×JST日付のユニーク)で数える。**人ごとに全店合計**で数える(店舗ごとではない)
- 対象は奨学スタッフのみ。オーナー・副担当は対象外
- 来店時は指定箇所のうち2箇所を清掃
- 試験前免除がある(欠席予定として登録、回数の分母から外す)
- 店舗ごとに清掃の型が違う。2026-11 時点で奨学スタッフは西新のみ在籍。桜坂と原四つ角は募集中で、いまは運営側が週1回ほど巡回する(頻度は状況で変わる)。だから「毎日の店 / 週次巡回の店」の型と、頻度をルールで上書きできる仕組みが要る
- 休業日・祝日: 現行での決定は記録なし。新規の既定値「回数に数えない」をそのまま採用し、README には「既存運用で未決だった項目」と正直に書く

## 5. 並走の形(11/4〜)

- スタッフは**同じ店舗チャンネル**に写真か一言を投稿する。新しい操作を覚えさせない
- 報告先は Slack を基本にする。既存の Notion フォームは止めないが予備。新しい仕組みは Notion を読まないので、Notion で送った報告は新しい仕組みには届かない。だから Notion 経由で報告した人が「入室したのに報告なし」と検出されうる → 承認を通す理由がここにもある。数字は「検出N件のうち、確認して本当に未報告だったM件」と出す
- 実際に突き合わせが動くのは西新店(奨学スタッフが在籍する唯一の店)。桜坂・原四つ角の入室は運営側か会員なので、検出対象にならない
- 既存の Notion オートメーションが西新チャンネルに投稿するボット発言は、新ボットが無視する(bot_id / subtype を見て弾く)
- 新ボットの受付返事はスレッドに返し、チャンネルを汚さない。備品依頼・トラブル・雑談には返さない

### RemoteLOCK の Webhook
- 管理画面「高度な機能 → お知らせ機能 → 通知先 → Webhook」に既存 Worker の通知先が1件ある。「通知先の追加」で2つ目を並べられる → **転送方式は不要。既存の通知先・お知らせ設定には一切触らない**
- 登録は新 Worker の `/events/entry` が本番で 200 を返すのを確かめてから(RemoteLOCK には無効な Webhook を停止する処理があるため、先に登録しない)
- 会員も同じ鍵で入るので、会員の解錠も飛んでくる。新 Worker は名簿の解錠IDと一致しない解錠を保存せず捨てる(元ペイロードも残さない)
- 手順:
  1. 「通知先」タブ → 通知先の追加 → Webhook。名前は新リポジトリ名、URL は新 Worker の `/events/entry`、コンテンツタイプは JSON、Secret を設定(wrangler secret にも同じ値を入れ、署名検証に使う)、有効にチェック
  2. 「お知らせ機能」タブ → お知らせ機能の追加。イベントは `access_person_used` のみ(誰が開けたかが入る。`unlocked` も同時に飛ぶので、両方受けると入室が二重になる)。対象はアカウント全体(スタッフ以外は受け口で捨てるので、全店まとめてよい)
  3. 実店舗で1回解錠してもらい、「お知らせ履歴」タブと新 Worker のログで届いたことを確認。会員の解錠が保存されていないことも確認する
